# Phase 0 Plan: 问题验证与定位收敛

## 1. 阶段概述

Phase 0 是 SignalReach AI 的产品验证阶段，周期建议为 2 周。此阶段不以开发完整产品为目标，而是验证市场问题、目标用户、产品定位、首个垂直场景和早期宣传信息。

核心判断：

> 用户是否真的愿意为了“更快找到高质量、可解释、可触达的人选”付费？

Phase 0 的成功不取决于代码量，而取决于是否拿到足够真实的用户问题、搜索任务、付费意愿和可复用的市场表达。

## 2. 阶段目标

### 2.1 业务目标

- 确认首个垂直场景，建议优先验证 B2B outbound lead generation。
- 找到 5-10 个愿意持续提供反馈的早期用户。
- 收集至少 20 条真实 people search query。
- 完成第一版 waitlist 和 landing page 文案。
- 明确产品是否应该继续投入 Phase 1 技术 PoC。

### 2.2 产品目标

- 明确用户当前找人的工作流。
- 明确用户最痛的环节：搜索、判断、联系人丰富、外联，还是跟进。
- 定义“好结果”的标准。
- 定义第一版 benchmark 数据集。
- 准备 3 个可演示的手工 demo report。

### 2.3 宣传目标

- 建立初始公开叙事：filters are the wrong interface for finding people。
- 启动 waitlist。
- 发布 3-5 条 build-in-public 内容。
- 获得第一批关注者、试用者和访谈对象。

## 4. 核心假设

Phase 0 需要验证以下假设：

| 假设 | 验证方式 | 通过标准 |
| --- | --- | --- |
| 用户认为找高质量目标人群很慢 | 用户访谈 | 70% 访谈对象明确表达该问题高频且痛 |
| 用户愿意使用自然语言找人 | Demo query 测试 | 用户能自然描述目标，不需要复杂筛选器 |
| 用户关心推荐理由和证据 | 访谈和 demo report | 60% 用户要求查看来源或判断依据 |
| B2B outbound 是最适合首发场景 | 多场景访谈对比 | B2B 用户付费意愿和频率最高 |
| 用户愿意为高质量结果付费 | 价格敏感度问题 | 至少 5 个用户接受付费试点 |
| 外联草稿有价值，但自动发送不是 MVP 必需 | 访谈 | 用户愿意先使用草稿、复制和导出 |

## 6. 用户访谈计划

### 6.1 访谈目标

每次访谈要拿到以下信息：

- 用户当前如何找人。
- 一次 sourcing 的真实耗时。
- 当前使用哪些工具。
- 现有工具哪里不够好。
- 用户如何判断一个人是否合适。
- 用户如何找到联系方式。
- 用户如何写外联。
- 用户是否愿意为更好的结果付费。
- 用户是否愿意提供真实 query 做测试。

### 6.2 访谈结构

建议 30 分钟：

| 时间 | 内容 |
| --- | --- |
| 0-3 分钟 | 背景介绍和确认角色 |
| 3-10 分钟 | 了解当前找人流程 |
| 10-18 分钟 | 深挖痛点和成本 |
| 18-23 分钟 | 展示概念或手工 demo |
| 23-28 分钟 | 价格、试用和数据意愿 |
| 28-30 分钟 | 请求推荐其他访谈对象 |

### 6.3 关键问题

必问问题：

- 你最近一次需要找一批目标人是什么场景？
- 你当时的目标人群描述是什么？
- 你用了哪些工具和平台？
- 从开始搜索到拿到可联系名单花了多久？
- 哪一步最浪费时间？
- 你如何判断一个人值得联系？
- 你现在如何找邮箱、LinkedIn、X、个人网站或其他联系方式？
- 你会手动写个性化外联吗？
- 你认为一个“好结果”必须包含什么？
- 如果一个工具能给你 30 个带证据的高匹配人选，你愿意付多少钱？
- 你愿意给我们一个真实 query，让我们手工返回一份结果报告吗？

避免问法：

- 你会不会用我们的产品？
- 你喜欢这个 idea 吗？
- 如果免费你会用吗？

更好的问法：

- 你现在为这个问题花了多少时间或预算？
- 你上一次为类似工具付费是什么时候？
- 如果下周就能用，你会拿它做哪个真实任务？

## 7. Benchmark 计划

### 7.1 目标

建立第一版 people search benchmark，用来评估 Phase 1 技术 PoC 是否真的有效。

### 7.2 数据集规模

Phase 0 需要收集 20 条真实 query：

- 10 条 B2B outbound。
- 5 条 creator sourcing。
- 3 条 recruiting。
- 2 条 expert / networking。

### 7.3 每条 query 的结构

```yaml
id: b2b_001
scenario: b2b_outbound
raw_query: "Find US-based B2B SaaS companies with RevOps leaders..."
target_user: "Founder selling sales analytics software"
must_have:
  - role: "RevOps or Sales Ops"
  - company_size: "50-500"
  - region: "United States"
nice_to_have:
  - recent_sales_hiring
  - uses_salesforce_or_hubspot
disqualifiers:
  - consultants
  - companies_smaller_than_20
required_evidence:
  - profile_url
  - company_url
  - role_evidence
  - signal_evidence
success_criteria:
  - at_least_10_relevant_people
  - each_person_has_source
  - at_least_30_percent_contactable
```

### 7.4 标注标准

每个结果人工标注：

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| relevance | 0-3 | 是否符合目标 |
| evidence_quality | 0-3 | 证据是否充分 |
| contactability | 0-3 | 是否可触达 |
| confidence | low / medium / high | 人工判断置信度 |
| notes | text | 标注原因 |

### 7.5 Benchmark 验收标准

Phase 0 结束时必须有：

- 20 条 query。
- 每条 query 的合格标准。
- 至少 3 条 query 有手工完成的 demo result。
- 一份 benchmark README。

## 8. 手工 Demo Report 计划

### 8.1 目标

在产品还没开发完成前，用人工方式模拟产品最终输出，验证用户是否认可结果形态。

### 8.2 Demo Report 结构

每份 report 包含：

- 用户输入。
- 解析后的搜索条件。
- 搜索策略。
- 10-20 个推荐人选。
- 每个人的匹配理由。
- 证据来源链接。
- 联系方式或可触达渠道。
- 外联草稿。
- 风险或不确定性说明。

### 8.3 推荐 3 个 Demo

1. B2B outbound：找 RevOps / Sales Ops 负责人。
2. Creator sourcing：找 AI productivity 创作者。
3. Expert networking：找某个细分领域专家。

### 8.4 Demo 验收标准

- 用户愿意打开结果查看。
- 用户能指出哪些人选有价值。
- 用户认为结果解释比普通搜索列表更有帮助。
- 用户愿意把类似任务交给产品继续处理。

## 9. Landing Page 计划

### 9.1 页面目标

Landing page 的目标不是完整解释所有功能，而是让目标用户快速理解：

- 这个产品帮谁。
- 解决什么问题。
- 为什么和传统 lead database 不一样。
- 用户应该提交 waitlist 或预约 demo。

### 9.2 页面结构

建议结构：

1. Hero。
2. Problem。
3. How it works。
4. Example output。
5. Use cases。
6. Why different。
7. Waitlist / Book demo。
8. FAQ。

### 9.3 Hero 文案

推荐英文：

```text
Find high-signal people from a natural language description.

SignalReach AI searches across the web, explains why each person matches, and turns results into personalized outreach drafts.
```

推荐中文：

```text
用一句话找到高质量目标人选。

SignalReach AI 会跨网络搜索目标对象，解释每个人为什么匹配，并生成可编辑的个性化外联草稿。
```

### 9.4 CTA

主 CTA：

- Join the waitlist。
- Book a demo。

辅助 CTA：

- Submit a search query。
- See example report。

### 9.5 Waitlist 表单字段

最小字段：

- Email。
- Role。
- Company。
- Use case。
- One real search query。

建议问题：

```text
Describe someone you wish you could find faster.
```

## 10. 宣传计划

### 10.1 宣传原则

Phase 0 不要宣传“产品已经能自动帮你找所有人”。应该宣传问题、方法和构建过程。

核心观点：

- Filters are not enough for people search。
- Bigger lead lists are not better lead lists。
- AI people search needs evidence。
- Outreach should start from context, not templates。

## 12. Go / No-Go 标准

### 12.1 进入 Phase 1 的条件

满足以下条件时进入 Phase 1：

- 完成至少 15 个有效访谈。
- 至少 5 个用户愿意提供真实 query。
- 至少 3 个用户愿意继续成为 design partner。
- 至少 50 个 waitlist 注册或明确兴趣线索。
- 完成 20 条 benchmark query。
- 明确第一个垂直场景。

### 12.2 暂停或调整的条件

出现以下情况应暂停或调整：

- 用户觉得问题存在，但不愿付费。
- 用户只想要更大的联系人列表，不关心解释和证据。
- 目标场景过于分散，无法形成重复 workflow。
- 手工 demo 无法明显优于普通搜索。
- 合规风险远高于商业价值。

### 12.3 Pivot 方向

如果 B2B outbound 验证不佳，可考虑：

- Creator sourcing agent。
- Expert discovery for research teams。
- Recruiting research assistant。
- Company research and account intelligence。
- AI workflow layer for existing CRMs。
